## 1. 一页速览

**任务**：SemEval-2027 RETECO Track 1a。给定 query + 该 query 所属领域的语料（13 域、1,167,159 篇文档、
1,211 train / 519 dev query），输出文档排序；官方指标 domain-macro nDCG@10。

**系统**（三件套，全部开源模型、8 GB 单卡）：

| 阶段 | 组件 | 说明 |
|---|---|---|
| 一阶段 | `mxbai-embed-large-v1` dense 检索 top-100 | 用**完整 query**（标题式 query 会掉 0.06） |
| 精排 | `bge-reranker-v2-m3` 窗口化 cross-encoder | 标题式 query、250 token 窗 / stride 192、max-pool；在 1,211 条 train 上 listwise 微调 2 epoch |
| 融合 | 查询内 z-norm 后 1:1 加权求和 | 权重在 train 上拟合、从不在 dev 上调 |

**数字链**：官方 BM25 0.1147 → dense 0.2943 → +零样本 CE 融合 0.3249 → **+SFT CE 融合 0.3581**
（三种子 0.3561 ± 0.0029，对零样本 **+0.031 ± 0.003**，域聚类 CI 全部排除 0）。

**三句话结论**：

1. **能动的只有打分器本身。** 召回、分块、query 表示、融合形式、LLM 精排、加深候选池 —— 全部试过，
   在 8 GB 单卡预算下都停在 ±0.02 且 CI 反复跨 0；把零样本 CE 换成在 train 上微调过的 CE，是唯一
   （a）效应量够大（b）域聚类 CI 排除 0（c）跨种子复现 的改进。
2. **显式时间建模在 Track 1a 上不成立，而且是可解释的。** 十个探针、四类独立方法族（词面/语义/生成/约束）
   一起失败；天花板分析给出根因：**时间不一致 ≠ 不相关**——即使用 oracle 知道 query 时间区间去降权
   年份不符的文档，8 个有锚定域的 7 个 nDCG 反而下降。这是负结果，但它是论文的一半。
3. **"0.3581 不可复现"曾经是一个错误结论**，出自一次选错 epoch 的重训（§9）。第三个种子
   独立跑出 0.3575 之后才判定：融合形式是稳的，那次重训是离群点。

**还没做完**：test split 全量回放（law/quant 被 CPU 模式卡住，GPU 版已重排）、4 页 SemEval system
description、1 月正式测试集提交包。

## 4. 主线一：先把尺子校准（Phase 0 + 3）

**为什么先做**：所有后续比较都建立在"我算的分和官方一致"上。如果尺子是歪的，后面每个 Δ 都是噪音。

**做法**：用 starter-kit 的 gensim BM25 复现四个已发布基线 → 再用官方预建 Lucene 索引跑同一 BM25 →
跑零样本 BGE dense → 算 Recall@K 与"候选内理想重排"上界。

**结果**：官方链路四个基线**逐位**复现（IOTA dev 0.3309 / train 0.1563；Bitcoin dev 0.0370 / train 0.0856）。
但预建索引跑同一 BM25 得到 0.3852 / 0.0300——复现不了发布值，top-10 重合只有 ~60%。

**根因（Phase 3 查清）**：官方基线用 gensim 的 `LuceneBM25Model`，它把 BM25 模型**也应用于 query 一次**，
于是点积里 idf 出现两次（外加 query 长度归一化）；Lucene 只应用一次。证据链完整：
(a) 自建 Anserini 索引与官方预建索引分数**完全相同**（都是 0.0300）→ 索引本身没问题；
(b) 同一个 query/文档，官方 93.5363 vs gensim 公式手算 93.4127；Lucene 77.2161 vs 手算 77.1619 —— 两条公式各自被复算验证；
(c) 查询内词权重跨度 13.5 倍，idf 平方显著改变相对权重 → top-10 只有 60% 重合。

**教训**：`pytrec_eval` 在本机编不过 → 改用官方 `ir_metrics.py`，并用四个基线逐位复现来证明等价。
"复现不了基线"有两种可能——实现错，或对方实现和你不一样；本项目是后者，且能精确指出差在哪。

## 5. 主线二：时间模块的十次尝试（全负）与根因

**动机**：任务名就叫 temporal retrieval，第一条直觉必然是"把时间信息用起来"。语料只有 `id + content`，
gold 只有 12% 含年份，所以只能从文本里推时间。

**十个探针**（完整表见 `docs/PAPER_DRAFT.md` §5.4，此处按方法族归并）：

| 方法族 | 探针 | 结果 |
|---|---|---|
| 词面特征 | ① 年份/时间锚点/guidance 标记做 logistic 回归，长度与词面重叠做对照 | Bitcoin −0.023、Economics +0.023，方向在域间变号；对照特征两域都变差 |
| 语义相似 | ② 用 guidance 构造"时间陈述"，与候选算余弦；5 折 query 分组 CV + placebo | 真陈述 0.69 vs 假 0.38（确实有 query 特定信号），但对 dense 的增量 ΔAUC +0.00005 / +0.0065，远低于事前门槛 0.05–0.08 |
| 生成式 | ④ Qwen2.5-1.5B 把 query 分解成时间步骤；⑤ HyDE 生成 5 篇假设文档 | 0.2012 / 0.1613、0.1819 / 0.1529，均低于 dense（0.2171 / 0.1891） |
| 约束式 | ③ oracle 步骤融合（最优 w0）；⑦ 朴素 TACR 重排 | ③ 两域一升一降；⑦ 排序崩坏，无指标留存 |
| 训练侧 | ⑥ 用"年份不符"候选挖时间负例 | 五个域共 37–43 条 ≈ 0.4/query，太少，不可训练 |
| 门控 | ⑨ **唯一预注册的**：train 上拟合门控（CE 分数作特征），dev 只读一次，门槛 +0.02 | 152 条锚定 query 上 0.3862 → 0.3901，**Δ+0.0039**，差门槛 5 倍 |
| 诊断 | ⑩ 时间可观测性（能抽出年份的比例） | 文档 20.4–50.6%，query 6.7–57.8% |

**根因（Phase 8b 的天花板分析）**：把冻结候选按"年份是否落在 query 时间区间"排序，**用 oracle 知道
区间**去降权年份不符的文档——169 条锚定 query（8 域）上，**7 个域 nDCG 下降**
（politics 0.360→0.260、genealogy 0.330→0.254、hsm 0.313→0.263、history 0.305→0.248、
bitcoin 0.182→0.156、law 0.369→0.334），只有 economics 上升（0.189→0.193）；
更现实的"只把年份不符的推到队尾"变体也降 6/8（workplace 持平）。原因：能抽出年份的候选里
57–100% 的年份不在查询区间内，**其中很多是 gold**。

→ **"时间不一致 ≠ 不相关"**。这就是此前所有时间模块归零的统一解释：它们都在惩罚 gold。

**这条负结果的正确表述**（论文已按此改写）：不主张"时间建模无用"，只主张"在 Track 1a 这种无时间戳、
只能从文本推时间、且相关性判定与时间约束弱耦合的设置下，十个探针没有一个拿到可提交的增益"，
并给出天花板分析作为机制解释。

**流程上的自我修正**：早期内部草稿把这十个都叫"预注册负结果"，这是错的——只有第 9 个是严格预注册的
（冻结协议、事前门槛、dev 只读一次），1–2 是"跑前定了设计和门槛但没登记"，3–8/10 是探索性的。
论文已逐行标注协议强度，并明确写出这处更正。

## 6. 主线三：召回 vs 排序（Phase 1/5/6/8 + Phase 12 深度探针）

**Phase 0 的初步答案**：dense top-100 的 oracle@10 是 0.6488，实际 0.2171 → 瓶颈在排序。
**但这条结论后来需要分域限定**（见下）。

**Phase 1 的自我修正**（重要）：第一版 CE 直接喂 query+doc 512 token（`longest_first` 截断），
bge-reranker-base 只有 0.1195，"CE 不迁移"的结论几乎写进报告。查下去发现 query 中位 221 token、
最长 1017，doc 实际只剩 ~250 token 预算。修正为显式 q_cap + 文档窗口 + max-pool 后：

| 配置（Bitcoin dev） | nDCG@10 |
|---|---|
| bge-base 原始（512 截断） | 0.1195 |
| bge-base 单窗口 380 | 0.1089 |
| MiniLM-L6 全 query | 0.1704 |
| MiniLM-L6 标题式 | 0.2041 |
| v2-m3 全 query | 0.1577 |
| **v2-m3 标题式** | **0.2121**（与 dense 0.2171 的差 n.s.） |
| RRF(dense, v2-m3) 2:1 | 0.2311 |

**结论修正**：不是"CE 不迁移"，而是"强 CE 追平 dense、弱 CE 变差"，且"全量替换"是深度假象
（depth 5 → 0.2143，depth 100 → 0.1195）。截断和长度偏差都被数据否定：gold 96.4% token 可见，
within-query 长度相关 ≈ 0。

**最关键的一条诊断**：within-query AUC —— dense 0.760 vs bge-reranker 0.668。
**重排器对 gold 的判别力低于它要重排的检索器。** 这句话解释了后面所有"聪明干预"为什么归零：
换后处理不会改变打分器的判别力。要让数字动，只能换打分器本身（→ Phase 9 的 SFT）。

**Phase 5（query 表示）**：一阶段检索必须用完整 query（标题式在 Bitcoin dev 掉 0.06、Economics dev 掉 0.07）；
短 query 的收益只存在于重排器（它对长 query OOD）。→ 两视图：检索 full、精排 title。

**Phase 6（工程化）**：bge-large 更大但更差（四个大样本格子三个变差，Bitcoin dev −0.0602 显著，
合并加权 −0.015）——排除了 fp16、instruction、pooling、表示崩溃等各种解释后接受这个事实；
低成本 top-5 pairwise 把延迟从 11.8 s 压到 2.5 s，但 Bitcoin dev +0.050 与 train −0.011 方向相反，不稳定；
两视图 RRF 2:1 三格方向一致为正（+0.0131）但未显著。

**Phase 7（12 域泛化）**：RRF 1:4 query 级 +0.0461、域级 +0.0258 但域 CI [−0.010,+0.058] 含 0；
LOOCV "换新领域的诚实增益"只有 +0.015；law −0.090、workplace −0.093 反向——CE 单独就低于 dense 的域。

**Phase 8（强基座）**：TEMPO 的 30.4 / DiVeR 的 32.0 分别是 7B/4B 模型、1,730 query、v1.0 语料，
与本地 519 dev / v1.1 不可并排。能跑的替代里 mxbai-embed-large-v1 最强（12 域 0.2995）。
mxbai + v2-m3 标题窗口 + RRF 1:1 → 0.3246，配对 +0.0333 [+0.0188,+0.0479]，
**域聚类 +0.0252 [+0.0027,+0.0506]，本项目第一次 CI 排除 0**。

**Phase 12 深度探针（负）**：稠密池 Recall@100 0.6995 / @200 0.7783 / @500 0.8697；oracle@10 0.7446/0.8150/0.8939。
取 62 条"gold 在 100–500 名"的难 query，用 200 深池重排 → 域宏 **+0.0010**（CI [−0.0009,+0.0036]，9/13 域恰好 0.0000）。
**CE 对 100 名以后的文档打分接近地板**，加深池子只增加成本 → k=300 全量重排取消。

**分域修正**："瓶颈在排序"在总体上成立，但局部相反：27.7% 的 dev query（1-epoch 臂）得 0 分，
其中 **36% 的 top-100 里根本没有 gold**（2-epoch 臂：26.6% 零分 / 37.7% 无 gold）。对这些 query，
召回是决定性的，重排无从下手。

## 7. 主线四：监督微调与融合（Phase 9 → 9d → 12）

### 7.1 诊断先行

冻结 top-100 的 oracle nDCG@10 = **0.7446**，V1 只拿 0.320（约 5% 的排序空间）；
零样本 CE 的 within-query AUC 0.801 ≈ dense 0.806 —— 换后处理不动这个量。
→ 只有改打分器本身。这就是 SFT 的立项理由。

### 7.2 训练设置

13 域 train，1,071 个 query 组 / 2,876 正例 / 18,544 负例（70% 为难负例，由 `build_ce_train_groups.py` 造）；
listwise 目标、bf16、梯度检查点（峰值 5.5 GB）、最多 3 窗、max_len 320、max-pool。
基座 `bge-reranker-v2-m3`（567.8 M）——先跑的 pilot 用 base（278 M）只到 0.2301，说明训练回路有效但模型太弱。

### 7.3 V1 与 V1.1（Phase 9）

| 系统（dev, 519 query） | domain-macro（官方） | topic-macro |
|---|---:|---:|
| 官方 BM25 | 0.1147 | — |
| dense mxbai top-100 | 0.2943 | 0.2891 |
| V1 = dense + 零样本 CE, RRF 1:1 | 0.3166 | 0.3199 |
| dense + 零样本 CE, z 1:2 | 0.3193 | 0.3302 |
| dense + 零样本 CE, z 1:1 | 0.3249 | 0.3260 |
| dense + SFT CE(1ep), z 1:2 | 0.3274 | 0.3418 |

两个关键发现：

1. **同一个 run 集给出两个不同数字。** topic-macro 选出的最优权重是 1:2，domain-macro 选出的最优是 1:1。
   "在 dev 上挑权重"会挑出不同的东西 → 权重必须在 train 上拟合。
2. **`score_run.py` 有 bug**：对 run 中缺失的 topic 只在"存在的 topic"上求均值，官方记 0。修复后所有历史数字重算。

### 7.4 口径更正（Phase 9d，整个项目的转折点）

外部审阅指出 Evaluation Plan 写的是："nDCG@10 is computed for each query, averaged over the queries of
each domain, and then averaged over the 13 domains, so every domain counts equally"，且
"missing queries ... receive zero"。**官方口径是 domain-macro，项目此前一直按 topic-macro 报告。**

影响有两层：
- 融合权重重拟合后 **z 1:1 胜出**（train domain-macro 0.2612 vs 1:2 的 0.2596），1:2 的 "V1.1" 作废；
- SFT 的增益在正确口径下更大，但"预注册门槛"的表述必须更正：门槛登记时用的统计量是 topic-macro
  （dev ≥ V1+0.015），按登记口径 SFT−V1 = +0.0141 **未达**；它是在口径更正之后才"看起来通过"的。
  论文里如实写"登记的 topic-macro 门槛未达"，可以站得住的是：按官方口径，**只换 CE**（相对最强零样本
  基线 z 1:1 = 0.3249）增益 +0.0087、域聚类 CI [+0.0037,+0.0142]，是唯一排除 0 的单因素效应；
  +0.0170 是它与融合形式变化（+0.0083，CI 跨 0）的合计，不能整体记在监督训练名下。

### 7.5 权重敏感性（§5j）

审稿人真正会问的不是"最优权重是多少"，而是"+0.0087 是不是挑权重挑出来的"。`weight_sweep.py`（纯 CPU，33 秒）
把两条臂在 dev 上按 w ∈ {0.5 … 2.0} 重新融合：

- 融面在 ±0.008 量级上是**平的，没有单调趋势**——零样本臂自身的波动与 SFT 增益同量级；
- SFT 臂在 9 个权重里 7 个领先，w ≥ 0.85 的每个权重都领先；
- → 论文只主张**冻结权重（在 train 上用零样本臂拟合、从未在 dev 上调）下的 +0.0087**，不主张"权重鲁棒"。
  并说明：该权重的调参对象是**对照臂**，SFT 臂反而是欠调的一方，所以这个比较只会低估。

另外两个必须预备的问题，答案也在这里：
1. **"CE 单独 0.2742 < dense 0.2943，为什么要 rerank？"** —— 两者错误互补：dense 与 SFT CE 在 top-100 内
   的平均 Spearman 只有 **0.279**（1-epoch 臂 0.328），融合才有增益。单模型低不代表融合无用。
2. **"增益是不是只靠一两个域？"** —— w=1 时 10/13 域上行；最大正贡献 cardano（+0.0336，36 条 query），
   负贡献 bitcoin（−0.0080）。

### 7.6 2-epoch 臂（Phase 12）

只改 epoch 数与峰值学习率（1e-5 → 1.5e-5），dev 域宏从 0.3336 跳到 **0.3581**：

| 系统 | domain-macro |
|---|---:|
| 零样本 CE, z 1:1 | 0.3249 |
| SFT 1ep, z 1:1 | 0.3336 |
| **SFT 2ep（best@ep1）, z 1:1** | **0.3581** |

- vs 零样本：**+0.0332**，query CI [+0.0161,+0.0523]，domain CI [+0.0192,+0.0472]，188 升 / 78 降 / 253 平；
- 12 域（去 iota）0.3181 vs 0.2832（+0.0349）；n≥19 的 8 域 0.3267 vs 0.2985（+0.0282）→ 不是 iota 或小域带来的；
- CE 单独只有 0.2823（仍低于 dense），融合后 0.3581 → 收益来自互补；
- 九个权重的扫描**全为正**（+0.0089 … +0.0346），w=0.7/1.5/1.8 时 13/13 域全升；
- **但要注意**：best 出现在 epoch 1（val 0.3029 → 0.3012），实际用的是"一个 epoch、峰值 1.5e-5、cosine 半程"的权重，
  所以这更像**学习率/有效训练量**效应，而不是"多训了一轮"。这一点在 §9 的反转里是关键。

## 9. Phase 11：一次"否定自己"的实验，以及它为什么出错

### 9.1 目的

审稿人（GPT review P1 #1）要求：融合权重必须在**训练集内部**做 out-of-fold 拟合，
这样才能证明 0.3581 不是"在 dev 上挑权重挑出来的"。

### 9.2 设计

重训 CE 时用 `--dump-val-qids` 留出 45 条 train query → 在这 45 条上拟合融合形式与权重 →
再把选出的权重套到 dev（dev 只读一次）。同时重训 1-epoch（e1b）和 2-epoch（e2b）两套。

### 9.3 结果

| 口径 | 值 |
|---|---|
| e2b checkpoint，z 1:1（即冻结形式） | **0.3196**（过期聚合；重算 0.3583，见 9.6） |
| e2b checkpoint，固定 RRF 1:1 | 0.3431（+0.0265，域 CI [+0.0052,+0.0473]） |
| e2b checkpoint，OOF 拟合 RRF 1:4 | 0.3187（+0.0206，query CI [−0.0037,+0.0435] 含 0） |
| OOF 在 45 条上的选择 | RRF dense:CE = 1:4 |
| 预注册门槛：SFT@OOF ≥ 零样本最好形式 0.3249 + 0.005 | **未达到** |

当时的结论：**"固定形式下 SFT 的增益是真的（+0.0265），脆弱的是 z 1:1 这个融合形式；0.3581 不可复现。"**
论文据此改写：可复现系统 = 0.3431，0.3336/0.3581 降级为 dev-selected fusion forms。

### 9.4 三个当时被忽略的疑点

1. **e2b 是四个 checkpoint 里唯一选 epoch 2 的**：val 0.2833 → 0.2871（升），而 s17/s23/s29 都选 epoch 1
   （s17: 0.3029 → 0.3012，s23: 0.2754 → 0.2684，s29: 0.3195 → 0.3054）。结合 §7.6 的观察——2-epoch 的收益
   其实主要来自"峰值 1.5e-5、cosine 半程"——选 epoch 2 等于把那个真正有效的权重停掉了。
2. **单域异常**：e2b 的 law 只有 **0.2093**，而 s17 0.4357、s23 0.4299。一项就占域宏差 0.017。
   其余小域也同向偏差（economics +0.054、genealogy +0.045、iota +0.088、politics +0.043、quant +0.043）。
3. **45 条 query 上拟合权重本身就是噪声**：45 条的 SE ≈ 0.02，是效应量的 ~2 倍。用它去选 8 个候选权重，
   选出来的东西和掷骰子差别不大。NEXT_STEPS 里其实已经写了 "CLOSED BY DECISION (C′)" 的理由，
   但 Phase 11 仍然把这个 45 条的选择当成"判决"。

### 9.5 与此同时，Phase 11 也做对了三件事

- 用错底座的事故被脚本守卫抓住，产物隔离、结论作废——没有污染主线；
- 固定的 RRF 1:1 下 SFT 仍然 +0.0265 且域 CI 排除 0 → SFT 有效这件事本身被独立确认；
- 它把"融合形式"和"checkpoint"两个因素分离开了——虽然分离的结果被误读，但实验设计是对的。

**教训**：一次重训的结果，只有在**同一配方、同一 checkpoint 选择规则**下重复出现，才能用来否定原结论。
Phase 11 改变了训练集（留出 45 条）、改变了量（567.8M 但不同 seed/split），却只保留了"2 epoch"这个标签，
然后用它去否定"2-epoch 0.3581"。这是**归因错误**，不是数据错误。

### 9.6 更正（2026-11-10 05:2x）：0.3196 是过期聚合

05:2x 复算时发现 `results/aggregate_sub_sft_e2b_dev.json` 里的 0.3196 **不是**当前 run 文件的结果：

- 该 JSON 的 `tag` 从 `sft_e2b` 改成了 `sub_sft_e2b`，但引用的 **score 文件路径没变**；
- 用当前的 `runs/fused_sft_e2b_bitcoin_dev.trec` 重跑 `score_run.py` 得 0.214096，与新存档**逐位相同**；
- 说明 03:53–03:58 期间 score 文件被按当前 run 文件重算覆盖过一次，旧的 0.3196 是重算前的产物。

重算后的同一 checkpoint：**z 1:1 = 0.3583**（topic 0.3680）、RRF 1:1 = 0.3431、OOF RRF 1:4 = 0.3187（后两者重算后不变）。
逐域也从 law 0.2093 → 0.4259、economics 0.1899 → 0.2376、genealogy 0.3595 → 0.4074。

**因此 §9.4 的三条"疑点"、§10.2–10.3 的 epoch-2 归因全部作废**：不是那次重训踩空，
而是那份聚合在写结论时已经过期。教训升级为：**结论只能从"当前文件可重算"的数字里取，
报告前必须用 run 文件重算一遍 score**（这条现在写进了 `results/PHASE11_VALIDATION.md` 与提交脚本的指纹契约）。

## 12. 方法学教训（按踩坑顺序）

1. **口径先定**。topic-macro 与 domain-macro 差 0.003–0.01，足以改变"最优融合权重"的选择；同一个 run 集能给出两个不同数字。报告必须写清口径。
2. **预注册门槛要连同"用哪个统计量"一起登记**。口径改了之后门槛"看起来通过"是假象，必须如实写"登记口径未达"。
3. **冻结候选再比较排序器**，否则测的是召回不是排序。任何 oracle/Recall 数字必须带候选深度。
4. **深度一致**：depth-5 与 depth-100 的实验不可并排（"CE 不迁移"的假结论就是这么来的）。
5. **配对 bootstrap + 域整群重采样**：域等权的指标必须在域层做 CI，否则"13 个域里 10 个上行"会被当成显著。
6. **名字不是证据**。tag/目录名里写 v2-m3 不代表真用了它；日志里的 `model` 与 `params_m` 才是。→ 守卫脚本。
7. **在几十条 query 上拟合超参等于掷骰子**。45 条时 SE≈0.02，是效应量的 2 倍。样本不够就不该做选择，应该冻结继承值并披露。
8. **8 GB 单卡上任何加载模型的任务都不能与训练并行**（已 OOM 3 次）；长训练必须 detached，宿主约 10 分钟会静默杀后台作业。
9. **小模型的 listwise = 复读**。判定方法：把候选整体反转，若输出仍是 `[1]..[20]`，它输出的是位置不是相关性。（本项目 3 项证据确认）
10. **"时间不一致 ≠ 不相关"**。oracle 降权年份不符文档，8 域中 7 域变差——负结果的机制解释比负结果本身值钱。
11. **单模型 nDCG 低 ≠ 融合无用**。dense 与 SFT CE 的 Spearman 只有 0.279，互补性才是收益来源。
12. **一次重训的结果不能用来否定原结论**，除非配方、种子、checkpoint 选择规则全部一致（Phase 11 的归因错误）。
13. **负结果要成体系**：十个探针 + 一个天花板分析 + 一处协议强度更正，构成论文可辩护的一半；孤立的负结果只是失败记录。
